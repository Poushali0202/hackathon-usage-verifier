# Migration contract (pinned decisions)

Per app-development-docs 03 §2. Companion: [BINDINGS.md](./BINDINGS.md).
This file is the spec later stages build against. SQL is Stage 3; pipes and
`verifyApp`/`deployTo`/`@me` are Stage 2.

## Architecture

Backend is not an app-owned server. Verification runs in the catalog
`tool_python` node on the RocketRide engine (RestrictedPython, in-process):
the pinned Python evaluator reads the repository over the GitHub REST/raw API
with the judge's own token — no sandbox, no git clone, nothing on disk — and
fails closed on inaccessible, truncated, or incomplete repos. The LLM explains
after the verdict; it never writes tag, backbone, or score.

Catalog pipeline generation, app-local `.pipe` copies, `client.use({ pipeline })`,
`validate`/`deployTo`, and `verifyApp`/`addApp`/`publishApp('@me')` are Stage 2.
Until Stage 3, runs and custom targets stay in `appState`. Stage 3 reads and
writes them through `rocketride_sql` (`sql_1`) when the signed-in shell session
can reach the broker; otherwise the UI keeps `appState` and does not attach
personal Postgres.

No `hackjudge_*` custom nodes. No `new RocketRideClient()` in the app.

## Data model (config-as-data)

Stage 1 store is workspace `appState`:

- `runs: StoredRun[]` — id, name, event date, target, status, results, counts,
  `created_by` / `updated_by` actor stamps, timestamps
- `targets: TargetRecord[]` — custom targets only; the RocketRide preset is a
  code seed (`is_preset`), not a user row

Runtime settings (manifest schema, not `appState`):

- `hackjudge.judge-hack.graceDays` — integer, default 2
- `hackjudge.judge-hack.historyPenalty` — number, default 2
- `hackjudge.judge-hack.storeVariant` — `default` (`rocketride_sql`) or `external`
  (`db_postgres`, generator-only fallback; not deployed unless the broker is down)

Plan is entitlement, not a user-editable setting. The RocketRide name on the
preset and judge copy is the judged platform, not publisher branding.

Custom targets use eight generic signals and four architecture templates (a view
of those signals, not a new scorer). Organizers always describe the product
(types, tokens, architecture labels). Developer uses the team default weights
and tag cut-offs. Company and Organizers may persist per-target `weights` and
`thresholds`; the engine already reads those maps. Live deploy-ops APIs are out
of Stage 1 pending product discussion.

Stage 3 replaces `appState` runs/targets with staging-managed SQL when the
signed-in app can execute `SELECT 1` on `rocketride_sql`. An API-key probe is
expected to fail (`ROCKETRIDE_CLIENT_ID is not set`). Personal / open-source
DB credentials must not return. The generator still emits an `external`
`db_postgres` variant with the same node id `sql_1`; it is not deployed.

## Store choice

**Stage 1:** `useWorkspace()` `appState` + `prefs` + contributed settings.

**Stage 3 target:** staging-managed SQL through the platform SQL node. Personal
/ open-source DB credentials must not return. Fallback (only if the Stage 3
probe fails): external `db_postgres` variant, same node id, switched by an app
setting — not before Stage 3.

## Pipeline inventory (Stage 2)

Generated by `apps/judge-hack-ui/tools/gen-pipes.mjs`. Stable `project_id`s
are pinned in that script. Canonical copies live in
`apps/judge-hack-ui/src/pipelines/` (what the app imports and what Stage 2
validates/deploys). The generator also writes workspace `pipelines/` for
disk-based deploy tooling. The Design canvas may rewrite `project_id` on
watched `pipelines/` folders; do not treat those copies as identity.

1. **Judge Hack Python V1** (`3f6b9d2e-5c41-4a8f-9e07-6d2b8c1a4f53`) —
   `tool_python` at node id `python_1` (`allowedModules: urllib, html`,
   `timeout: 900`). The app sends the flat evaluator script plus a `JOB`
   literal and the judge's `TOKEN`, and reads the script's `result` dict.
   A dummy `agent_rocketride` is present only so the tool can be invoked via
   `client.tool`; it is instructed not to answer or invent JSON. The LLM never
   writes tag, backbone, or score. Batches use a pool of 2 workers (3 on
   Company / Organizers), one repo at a time per worker, capped at 5 per
   workspace. Explain starts only after those tokens are terminated.
   Replaces the retired Daytona pipe (`bde4acbb-…`).
2. **Judge Hack Explain V1** (`cf2762a0-ee71-4f77-9d99-1296e81e71b4`) —
   post-verdict prose only.

3. **Judge Hack SQL V1** (`8e2a6c14-b7f1-4d93-9a50-1c4e8f2d7b36`) —
   `rocketride_sql` at node id `sql_1`, `allow_execute` on. Literal
   `client.database.query` for schema, runs, and custom targets. External
   variant `c5d9e2b8-1a47-4f06-8d3c-9b7e0a4f2c18` is generated only.

No schedules (`deploy.setSchedule` unused). Evaluator bytes ship as generated
TypeScript (`src/verify/generated/evaluatorBundle.ts`) so the server build
does not depend on a `.py` loader or `Projects/` imports.

## App plan

Scaffolded app id `hackjudge.judge-hack`. One mount, state-flag navigation,
`AppLayout` sidebar, `useAuthUser` identity, `usePrefs` / `useWorkspace` state,
plain CSS on `--rr-*` plus Judge Hack tokens. Sheet parsing and Excel export
are frontend (SheetJS).

Manifest: `authenticated: true`, `mode: "subscription"`, three one-time plans
(Developer 2000¢ / Company 10000¢ / Organizers 20000¢ USD), settings schema
above. Checkout is `shell:subscribe` without a fake `price_*`. Company-gated
features also unlock for Organizers.

## Identity

Every write stamped from `useAuthUser()` via `actorFrom()` (`userId` required;
email and displayName optional). No hardcoded actor names.

## Cross-language equivalence

The evaluator stays Python (`tool_python`). TypeScript owns UI, sheet I/O, stamps,
and entitlement mapping. No mirrored scoring logic to keep in sync.

## Acceptance gates

1. `tsc --noEmit` clean, `npm test` green (Vitest on UI/data helpers + evaluator
   `test_stage1.py`), and `rsbuild build` green (Stage 1 UI/data port).
2. Verdict parity against the in-process engine (Stage 2 pipes / later).
3. SQL counts + read paths after export/import (Stage 3). The signed-in app
   hydrates from `hj_runs` / `hj_targets` or keeps `appState` if the broker
   is down.
